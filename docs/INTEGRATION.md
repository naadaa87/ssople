# 쏘플파티룸 시스템 연동 규격

네 개 시스템이 어떻게 맞물려 도는지 정리한 문서입니다.
어느 한쪽을 고칠 때 다른 쪽이 깨지지 않도록, 서로 지켜야 할 약속을 적었습니다.

---

## 1. 전체 그림

```
                        ┌─────────────────────────┐
                        │   D1  ssople  (하나)     │
                        │                          │
  고객 홈페이지 ────────▶│  branches                │◀──────── 호스트 홈페이지
  ssople-front          │  branch_photos           │          ssople-host
  (이 저장소)            │  reservations  ★핵심     │          (점주·매니저·스태프)
                        │  users                   │
      쓰기: 예약 · 결제  │  settlements             │   쓰기: 예약 · 지점정보 · 정산
      읽기: 지점 · 예약  │  bot_faqs / bot_policies │   읽기: 전부
                        │  customers · payments    │
  AI 챗봇 ──────────────▶│  reviews · web_settings  │◀──────── 본사 대시보드
  ssople-chatbot        └─────────────────────────┘          (읽기 전용)
  (읽기 전용)
```

**데이터베이스는 하나입니다.** 이게 가장 중요합니다.
따로 만들면 홈페이지 예약이 점주 화면에 안 뜨고, 같은 시간에 두 팀이 예약됩니다.

---

## 2. 각 시스템이 하는 일

| 시스템 | 쓰는 사람 | 하는 일 | 주소(예) |
|---|---|---|---|
| **고객 홈페이지** (이 저장소) | 손님 | 지점 탐색, 예약, 예약금 결제, 취소, 후기 | `www.ssople.co.kr` |
| **호스트 홈페이지** | 점주·매니저·스태프 | 예약 관리, 지점 정보, 정산 조회, 외부 예약 등록 | `host.ssople.co.kr` |
| **본사 대시보드** | 본사 운영팀 | 전사 지표, 승인, 정산 확정, 통계 | `admin.ssople.co.kr` |
| **AI 챗봇** | 손님 (카카오 채널) | 문의 응대, 예약 안내, 상담원 이관 | Worker |

역할이 겹치지 않게 나눠 놓았습니다.
**고객 홈페이지에는 점주 화면도 관리자 화면도 없습니다.** 그건 호스트와 대시보드의 몫입니다.

## 3. 공유 테이블 — 서로 지킬 약속

### 3.1 `reservations` — 네 시스템이 함께 보는 표

이 표의 컬럼과 값은 **누구도 마음대로 바꾸지 않습니다.** 바꿔야 하면 네 곳을 함께 고칩니다.

| 컬럼 | 값 | 누가 씁니까 |
|---|---|---|
| `slot` | `day` \| `night` | 전부 |
| `status` | `waiting` \| `confirmed` \| `completed` \| `canceled` \| `noshow` | 전부 |
| `source` | `web`(홈페이지) \| `manual`(점주 수기) \| `external`(외부 채널) | 전부 |
| `refund_type` | `full` \| `none` | 홈페이지·호스트 |
| `deposit_amount` | 예약금 (홈페이지 결제분) | 홈페이지 |
| `total_amount` | 총 이용 금액 | 전부 |
| `customer_id` | 홈페이지 회원이면 `customers.id`, 아니면 NULL | 홈페이지만 |

**상태값은 전부 소문자입니다.** 대문자로 쓰면 호스트 화면에서 안 보입니다.

### 3.2 홈페이지가 예약을 만드는 방식

```sql
INSERT INTO reservations
 (code, branch_id, use_date, slot, name, phone,
  people_base, people_extra, base_amount, extra_amount, option_amount,
  total_amount, deposit_amount, status, source, request_note, customer_id)
VALUES (?,?,?,?,?,?, ?,?,?,?,0, ?,?, 'confirmed','web', ?,?)
```

`status='confirmed'`, `source='web'`으로 들어가므로
점주는 호스트 화면에서 **홈페이지 예약임을 바로 알아봅니다.**

### 3.3 이중 예약 방지

같은 지점·같은 날·같은 타임에 살아있는 예약은 **하나뿐**입니다.
DB 인덱스가 마지막으로 막습니다.

```sql
CREATE UNIQUE INDEX uq_res_slot
  ON reservations(branch_id, use_date, slot)
  WHERE status IN ('waiting','confirmed','completed','noshow');
```

홈페이지에서 결제가 끝나기 직전에 점주가 수기로 같은 타임을 넣으면,
홈페이지 쪽 INSERT가 실패하고 **결제금이 자동 환불됩니다.**
그 기록은 `audit_logs`에 '중복 예약 차단'으로 남습니다.

### 3.4 결제 진행 중 잠금(홀드)

홈페이지는 결제 화면에 들어가는 순간 그 타임을 **10분간 잠급니다.**
잠금은 KV에 두고, 시간이 지나면 저절로 풀립니다.

> 호스트 쪽에서도 이 잠금을 존중하려면 예약 등록 전에
> KV의 `hold:{branchId}:{date}:{slot}` 키를 확인하면 됩니다.
> 확인하지 않아도 위의 유니크 인덱스가 사고를 막습니다.

## 4. 챗봇 연동

### 4.1 붙어 있는 주소

```
CHATBOT_URL  = https://ssople-chatbot.naadaa87.workers.dev
CHATBOT_PATH = /skill
```

### 4.2 브라우저가 챗봇을 직접 부르지 않습니다

챗봇은 카카오 오픈빌더용 스킬 서버라 브라우저에서 바로 부르면 CORS에 막히고,
주소와 키가 화면 코드에 드러납니다. 그래서 홈페이지 서버가 대신 부릅니다.

```
브라우저 → /api/chat  (홈페이지 서버)
              → https://ssople-chatbot…workers.dev/skill
```

**카카오톡에서 물어본 답과 홈페이지에서 물어본 답이 같습니다.**
답변 규칙을 두 군데 두면 반드시 어긋나기 때문에, 규칙은 챗봇 한 곳에만 둡니다.

### 4.3 주고받는 것

보낼 때는 카카오 스킬 규격 그대로입니다.

```json
{
  "userRequest": {
    "utterance": "강남점 주차 되나요?",
    "user": { "id": "web-<세션>", "type": "web" }
  },
  "action": {
    "clientExtra": { "channel": "web", "page": "room-detail.html", "branchName": "강남점" }
  }
}
```

- `user.id` 를 세션마다 고정해 두어서 앞뒤 대화가 이어집니다.
- `clientExtra` 로 지금 보고 있는 화면을 함께 알려줍니다.
  챗봇이 쓰지 않아도 무해하고, 쓰면 "이 지점" 같은 질문이 자연스러워집니다.

받는 쪽은 카카오 스킬 응답 규격을 그대로 받아 화면용으로 정리합니다.
`simpleText` · `basicCard` · `textCard` · `itemCard` · `listCard` · 단순 `{answer}` 를 모두 처리하고,
버튼의 `webLinkUrl` 은 바로가기 링크로, `phoneNumber` 는 전화 링크로 바꿉니다.
`quickReplies` 는 `messageText` 가 있으면 그것을 보냅니다.

응답 처리는 `npm run test:chat` 으로 14가지 형태를 검증할 수 있습니다.

### 4.4 챗봇이 죽어도 상담창은 삽니다

9초 안에 응답이 없으면 같은 D1의 `bot_faqs` 로 답합니다.
환불·취소·보증금처럼 한 글자도 달라지면 안 되는 것은
`is_fixed=1` 문구를 그대로 내보내므로, 장애 중에도 규정 답변은 흔들리지 않습니다.

연결 상태는 `/api/chat/health` 를 브라우저로 열어 확인합니다.

### 4.5 화면 어디에 붙어 있나

| 위치 | 동작 |
|---|---|
| 전체 20개 화면 | 오른쪽 아래 상담 버튼 |
| 지점 상세 | 지점명을 물고 들어가 "강남점 주차 되나요?" 같은 추천 질문이 뜸 |
| 예약·결제 화면 | **넣지 않았습니다** — 10분 잠금이 걸려 있어 다른 화면으로 새면 자리를 놓칩니다 |

기존 페이지에 이미 있던 상담창 마크업을 그대로 쓰고 안쪽 동작만 갈아끼웠습니다.
버튼이 두 개로 늘어나지 않습니다.

### 4.6 챗봇 쪽에 넣어줄 홈페이지 주소

챗봇 `wrangler.toml` 의 경로 변수를 홈페이지 실제 파일명에 맞춰주세요.
안 맞으면 챗봇이 보내는 버튼이 없는 페이지로 갑니다.

| 용도 | 경로 |
|---|---|
| 사이트 주소 | `https://www.ssople.co.kr` |
| 예약하기 | `/rooms.html` |
| 지점 상세 | `/room-detail.html?id={branchId}` |
| 날짜 지정 검색 | `/rooms.html?date=YYYY-MM-DD&region=서울` |
| **예약 조회** | `/lookup.html` — 예약번호+연락처, 로그인 없이 열림 |
| 예약번호 바로 조회 | `/lookup.html?code=SP26082001` |
| 이용안내 | `/guide.html` |
| 지점 안내 | `/locations.html` |

### 4.7 챗봇이 읽는 것

챗봇은 같은 D1을 **읽기 전용**으로 씁니다.

- `branches` — 지점 정보, 요금, 주차, 편의시설
- `reservations` — 예약 가능 여부
- `bot_faqs`, `bot_policies` — FAQ와 정책

챗봇은 자기 대화 기록을 자기 테이블에 남기고, 홈페이지 상담창 기록은
홈페이지의 `chat_logs` 에 마스킹된 상태로 따로 남습니다.

## 5. 호스트 홈페이지와의 관계

### 5.1 지점 정보는 호스트가 주인입니다

`branches`의 요금·인원·편의시설·이용안내는 **호스트에서 점주가 관리합니다.**
홈페이지는 읽기만 합니다. 홈페이지에서 지점 정보를 고치는 화면은 없습니다.

다만 홈페이지 화면에 필요한 컬럼 몇 개를 `branches`에 더 붙였습니다.

| 컬럼 | 용도 |
|---|---|
| `region` | 지역 필터 (서울/경기/…) |
| `lat`, `lng` | 지도 표시 |
| `tags` | 목적 태그 `["생일","바베큐"]` |
| `day_start/end`, `night_start/end` | 타임 시각 표시 |

`schema/000_alter.sql`이 이 컬럼들을 붙입니다. 호스트 쪽 코드에는 영향이 없습니다.

### 5.2 정산은 호스트가 합니다

홈페이지는 **정산을 건드리지 않습니다.**
`settlements`, `settlement_items`에 쓰지 않고 읽지도 않습니다.

호스트가 정산할 때 홈페이지 예약도 자동으로 잡힙니다.
`reservations`에 `total_amount`가 들어 있기 때문입니다.

> **정산 시 주의** — 홈페이지 예약은 `deposit_amount`(예약금)만 카드로 결제됐고
> 잔금은 현장에서 받습니다. 정산 기준을 `total_amount`로 잡을지
> 실제 수납액으로 잡을지는 운영 규칙에 따라 호스트에서 정합니다.

### 5.3 계정은 따로입니다

| | 테이블 | 로그인 |
|---|---|---|
| 고객 | `customers` | 휴대폰 + 비밀번호 |
| 점주·스태프 | `users` | 휴대폰 + 비밀번호 |

두 테이블 모두 **비밀번호를 같은 방식으로 저장합니다** (PBKDF2 100,000회, `password_hash` + `salt` 분리).
나중에 계정을 합치더라도 문제가 없습니다.

고객 홈페이지 로그인 화면에서 점주 계정으로는 로그인되지 않습니다.
안내 문구로 호스트 사이트를 알려줍니다.

## 6. 정기 작업이 겹치지 않게

홈페이지와 호스트 양쪽에 배치가 있습니다. **역할을 나눴습니다.**

| 작업 | 담당 |
|---|---|
| 이용 끝난 예약을 `completed`로 | 양쪽 (`source='web'`만 홈페이지가 처리) |
| 방문 전날 안내 · 후기 요청 | **홈페이지** |
| 회원등급 재산정 | **홈페이지** |
| 정산 집계 · 마감 | **호스트** |
| 점주 알림 · 메시지 할당량 | **호스트** |

홈페이지 배치는 `UPDATE ... WHERE source='web'` 조건이 붙어 있어
호스트가 이미 처리한 예약을 다시 건드리지 않습니다.

## 7. 무엇을 바꿀 때 무엇을 함께 봐야 하는가

| 바꾸는 것 | 함께 확인할 곳 |
|---|---|
| `reservations` 컬럼·상태값 | 홈페이지 · 호스트 · 대시보드 · 챗봇 **전부** |
| `branches` 요금 구조 | 홈페이지 예약 위젯, 호스트 지점 관리, 챗봇 요금 안내 |
| 환불 규정 | `web_settings.refund.rules` (홈페이지) + 호스트 환불 처리 + 챗봇 고정응답 |
| 예약금 금액 | `web_settings.deposit.amount` + 챗봇 `bot_policies` |
| 타임 시각 | `branches.day_start` 등 + 챗봇 지점 안내 문구 |

**환불 규정과 예약금은 세 군데에 적혀 있습니다.** 하나만 고치면 답이 서로 달라집니다.
바꿀 때는 반드시 셋 다 확인하세요.

## 8. 연동 점검 항목

배포 후 이 순서로 확인하시면 됩니다.

- [ ] 홈페이지에서 예약 → **호스트 예약 목록에 바로 뜨는가**
- [ ] 호스트에서 수기 예약 등록 → **홈페이지에서 그 타임이 마감으로 보이는가**
- [ ] 같은 타임을 홈페이지와 호스트에서 동시에 등록 → **한쪽만 성공하고 나머지는 자동 환불되는가**
- [ ] 홈페이지에서 취소 → **호스트에 `canceled` / `refund_type`이 함께 반영되는가**
- [ ] 챗봇에 환불 질문 → **홈페이지 규정과 글자까지 같은 답이 오는가**
- [ ] 챗봇에서 "예약 조회" → **`/lookup.html`이 열리고 조회되는가**
- [ ] 홈페이지 상담창 → **카카오 챗봇과 같은 답이 오는가**
- [ ] `/api/chat/health` → **`connected: true` 가 나오는가**
- [ ] 지점 상세에서 상담창 → **그 지점 이름이 붙은 추천 질문이 뜨는가**
- [ ] 챗봇 서버를 잠시 내림 → **홈페이지 상담창이 FAQ로라도 답하는가**
- [ ] 대시보드 매출 = 호스트 정산 = 홈페이지 결제 합계 → **세 숫자가 맞는가**
